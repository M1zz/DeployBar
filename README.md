# DeployBar

fastlane 없이 여러 iOS/macOS 앱을 **메뉴바에서 관리·배포**하는 순수 Swift macOS 앱.
Node·로컬 서버 불필요. 앱을 열면 끝, 종료하면 잔류 프로세스 0.

다국어 앱은 **버튼 하나로** 게이트 → 빌드 → 업로드 → *지원 언어 전부의* 릴리즈노트까지 끝난다.

## 열기 / 실행

```bash
open DeployBar.xcodeproj      # Xcode 에서 열고 ⌘R 로 실행
```

메뉴바 우측 상단에 🚀 아이콘이 뜬다. 클릭하면 앱 카드·상태·배포 버튼이 나온다.

> 첫 실행 시 서명은 Xcode 가 개발팀(QGAQ3AY3R3)으로 자동 처리한다.
> 다른 팀이면 프로젝트 설정 또는 `project.yml` 의 `DEVELOPMENT_TEAM` 을 바꾼다.

## 화면 읽는 법

기억할 게 없도록, **지금 뭐가 필요한지를 화면이 먼저 말한다.** 헤더의 `?` 버튼이 앱 안 사용법이다.

```
🟢 5 배포 가능  🔒 21 막힘  ✅ 5 배포됨  ✨ 30 설정 필요    31개 앱  ↑↓ ? ⟳   ← 칩을 눌러 거른다
──────────────────────────────────────────────────────────────
  두번알림                                        [🔒 잠김 1] [📄] [⋯]
● v2.2.2(2) · 스토어 v2.2.1 · 제출 준비
  ⚠️ 커밋되지 않은 변경 → 커밋하면 풀림   9/10 ▾    ← 누르면 펼쳐짐
──────────────────────────────────────────────────────────────
  배포 준비 9/10 ▓▓▓▓▓▓▓▓▓░              [📋 해결 프롬프트]
    ❌ 커밋되지 않은 변경                              [📋]
       브랜치 dev 에 저장 안 된 변경이 있습니다
       → 변경사항을 커밋한 뒤 배포하세요
    ⚠️ 번역 구멍 2건 — 일본어 1, 한국어 1              [📋]
    ✅ 통과한 9가지 ▾                                ← 접혀 있음
```

**같은 말을 두 번 하지 않는다** — 40개가 세로로 늘어서는 화면이라 이게 곧 디자인이다.

| 자리 | 말하는 것 |
|---|---|
| 왼쪽 **점** | 상태. 🟠 잠김 · 🟣 심사 중 · 🔵 배포 가능(권장 남음) · 🟢 배포 가능/배포됨 |
| **버전 줄** | 로컬 v · 스토어 v · App Store 쪽 상태(제출 준비·심사 중 …) |
| **요약 줄** | 무엇이 막고 있고 → 뭘 하면 풀리는지. 뒤의 `9/10` 은 준비된 항목 수 |
| **오른쪽 버튼** | 지금 할 수 있는 일 하나. `[배포]` · `[🔒 잠김 N]` · `배포됨` |

- **잠겨도 길은 있다.** `⋯ › 잠긴 채로 그래도 배포` 가 체크리스트를 건너뛰고 배포를 시작한다
  (배포 자체의 검사 — 원격 받기·다국어·릴리즈노트 — 는 그대로 돈다). 잠금은 대부분 옳지만
  늘 옳지는 않으므로, 사람이 판단해서 밀어붙일 자리를 남겨 둔다. 심사 중인 앱에 이미 있던 길과 같은 결이다.
- **조회를 못 한 것으로는 잠그지 않는다.** App Store Connect 가 429·5xx 를 주거나 네트워크가 끊기면
  ⚠️ `App Store 상태를 확인하지 못함` 으로만 표시하고 배포는 열어 둔다 — 업로드는 altool 이 하므로
  조회 실패는 배포를 막을 근거가 아니다. 반대로 **번들 ID 로 앱을 못 찾거나 키가 잘못된 것은 잠근다**
  (altool 도 같은 키를 쓴다). 규칙은 `--selftest-lock` 이 지킨다.
- **`[🔒 잠김 N]` 은 눌러진다.** 못 누르는 회색 버튼 대신 **왜 잠겼는지를 펼쳐 주는 버튼**이다.
  (macOS 에서 비활성 버튼은 툴팁조차 안 떠서 이유를 알 길이 없다)
- **`9/10` 을 누르면** 손볼 항목이 펼쳐진다. 통과한 것은 `✅ 통과한 9가지 ▾` 한 줄로 접혀 있다 —
  다 됐는지는 숫자로 확인되고, 9줄을 늘어놓을 이유는 없다.
- **`[자동 설정]`** = 버튼 한 번으로 끝나는 것 (deploy.env·검사 스크립트 생성, 경로 정정)
- **`[📋 해결 프롬프트]`** = 남은 항목을 **그대로 지시문으로 만들어 클립보드에 넣는다.**
  Claude Code 등에 붙여넣으면 된다. 항목 옆 `📋` 는 그 항목 하나만. CLI 로는 `--prompt 앱이름`.
  `[자동 설정]` 이 되는 항목엔 안 붙는다 — 버튼이 더 빠르다.
- **스크린샷이 낡으면 체크리스트가 먼저 말한다.** 그림을 찍은 뒤로 화면 파일이 바뀌었으면
  ⚠️ `스크린샷이 화면 변화보다 오래됐습니다` 가 뜨고, 그 줄의 **`[프롬프트 복사]`** 버튼이
  다시 찍을 지시문을 클립보드에 넣는다 — "가끔 있는 그때" 를 사람이 기억하지 않아도 된다.
  **배포는 막지 않는다**(⚠️ 권장). 찍은 뒤 `⋯ › 스토어 페이지 › 스토어에 올리기` 가 그 그림을 올린다.
  `docs/screenshots/` 가 없는 앱에는 아예 뜨지 않는다 —
  이 워크플로를 안 쓰는 앱에 고칠 생각 없는 경고를 붙이지 않기 위해서다.
- **`⋯ › 앱스토어 그림 프롬프트`** = (낡지 않았어도) 언제든 같은 지시문을 꺼낸다.
  DeployBar 는 그림을 **만들지는 않고 올리기는 한다**(`⋯ › 스토어 페이지`). 대신
  **무엇을 다시 찍어야 하는지**는 이쪽이 안다 —
  지금 걸린 그림이 언제 찍혔는지, 그 뒤로 어느 화면 파일이 바뀌었는지, 이번 버전이 스토어에서
  뭘 자랑한다고 써 뒀는지(RELEASE_NOTES.md), 제출 규격이 얼마인지를 한 장으로 적어 준다.
  그대로 Claude Code 에 붙여넣으면 시뮬레이터로 찍는다. CLI 로는 `--shots 앱이름`.
- **🟣 심사 중은 '배포 가능' 과 다르다.** 내가 제출 버튼을 눌러 애플이 보고 있는 상태(`심사 대기`·`심사 중`·
  `출시 대기`)다. 여기서 새 빌드를 올리면 **그 심사가 취소되고 처음부터 다시 시작한다.**
  그래서 배포 버튼 자리에 `[심사 대기]` 가 오고, 한 번 눌러 배포되지 않는다.
  정말 다시 올려야 하면 `⋯ › 심사 취소하고 다시 배포` 로만 닿는다. `[전체 배포]` 대상에서도 빠진다.
  `제출 준비`·`거부됨` 은 **아직 안 낸** 상태라 배포해도 잃을 심사가 없다 — 그래서 🟣 가 아니다.
- **상단 요약 칩은 필터다.** 앱이 40개쯤 되면 "막힌 3개"를 눈으로 찾게 되므로, 칩을 누르면 그 분류만
  남는다. 다시 누르거나 오른쪽 `5/31개` 를 눌러 해제. 0개인 분류는 칩이 숨는다.
  순서 편집과 `[전체 배포]` 는 **늘 전체 기준**이라 필터에 영향받지 않는다.
- **버전 올리기·자동 설정·점검·Finder 열기** 는 `⋯` 안에 있다. 상시로 떠 있을 이유가 없다.

### 배포 순서

헤더의 `↑↓` 버튼이 순서 편집 모드다. **드래그**하거나 행의 `▲▼` 로 옮기며, 바꾸는 즉시 저장된다
(`apps.json` 의 배열 순서). `[전체 배포]` 는 이 순서대로 위에서부터 진행하고,
막힌 앱(❌)은 어차피 실패하므로 대상에서 빠진다 — 다만 **빠진 앱과 그 이유를 로그 맨 앞에 전부 적는다.**
"31개를 눌렀는데 22개만 돌았다" 의 이유를 로그 밖에서 찾게 하지 않는다. `이름순으로` 로 언제든 되돌릴 수 있다.

새로 만든 앱 폴더는 **목록 맨 뒤**에 붙는다 — 정해 둔 순서가 흔들리지 않는다.

배포를 막는 것과 권장에 그치는 것을 구분한다.

| ❌ 배포가 잠김 | ⚠️ 배포는 되지만 권장 |
|---|---|
| 커밋되지 않은 변경 | 배포 전 검사 스크립트 없음 |
| 올릴 변경 없음 / 로컬이 스토어보다 낮음 | 배포 설정(deploy.env) 없음 |
| 버전 파일 경로 오류 | 언어 목록 미선언 |
| App Store 앱 확인 실패 | 번역 구멍 (게이트가 `warn` 일 때) |
| 번역 구멍 (게이트가 `strict` 일 때) | 심사 대기 중 재업로드 |
| **릴리즈노트 비어 있음** (기본값 `strict`) | 릴리즈노트 (게이트가 `warn` 일 때) |
| | 스토어 페이지 미완성 (첫 출시 — 설명·그림·연령 등급) |
| | 버전에 빌드 미연결 → `[빌드 연결]` (보통은 배포가 알아서 붙인다) |

## 앱 쪽 규칙 — 관리 대상 앱이 갖춰야 할 것

`~/Documents/workspace/Auto/` 아래의 폴더 중 최상단에 `.xcodeproj`/`.xcworkspace` 가
있으면 자동으로 관리 대상이 된다. 그 위에 아래 규칙을 지키면 배포가 자동화된다.

| # | 규칙 | 없으면 | 강제성 |
|---|---|---|---|
| 1 | 앱 폴더 최상단에 Xcode 프로젝트 **하나** | 발견 자체가 안 되거나, 둘이면 엉뚱한 쪽을 씀 | **필수** |
| 2 | `deploy.env` — 배포 설정 | 폴더 이름을 scheme 으로 추정 (틀리면 실패) | 권장 |
| 3 | `Version.xcconfig` 에 `MARKETING_VERSION` + `CURRENT_PROJECT_VERSION` | `project.pbxproj` 를 정규식으로 직접 수정 (타겟이 여러 개면 위험) | 권장 |
| 4 | `scripts/predeploy.sh` — 배포 전 게이트 | 테스트 없이 배포됨 | 권장 |
| 5 | `.xcstrings` 의 모든 `LOCALES` 언어가 빠짐없이 번역 | 외국 사용자에게 한국어가 노출됨 | `LOCALIZATION_GATE` 에 따름 |

### `deploy.env` — 이 파일이 앱의 배포 규칙 전부

```sh
# 필수: archive 할 scheme
SCHEME=Rereminder

# 플랫폼 (ios | macos). 자동 판별이 맞으면 지워도 된다.
# 멀티플랫폼 타겟은 SDKROOT 만으로 구분되지 않아 명시해 두는 편이 안전하다.
PLATFORM=ios

# 권장: 버전·빌드번호의 단일 소스 (앱 폴더 기준 상대경로)
VERSION_XCCONFIG=Config/Version.xcconfig

# 권장: 배포 전 게이트. 실패하면 아카이브를 만들지 않는다.
PREDEPLOY_SCRIPT=scripts/predeploy.sh

# 다국어: App Store 에 등록한 언어. 이 목록이 곧
#   (1) 다국어 게이트의 검사 기준이고
#   (2) 릴리즈노트를 만들 언어다.
LOCALES=ko,en,ja

# strict — 번역 구멍이 하나라도 있으면 배포 중단 (다국어 앱 권장)
# warn   — 로그에만 남기고 진행 (기본값)
# off    — 검사 안 함
LOCALIZATION_GATE=strict

# 릴리즈노트 게이트 — '이 버전의 새로운 기능' 이 비어 있을 때
# strict — 배포 중단 (기본값). 빈 노트로 나간 버전은 되돌릴 수 없다.
# warn   — 경고만 하고 진행
# off    — 검사 안 함
RELEASE_NOTES_GATE=strict

# 업로드가 끝나면 빌드를 버전에 붙이고 심사까지 낸다 (기본 on).
# 사람이 할 일(인앱결제·연령 등급·가격·빈 릴리즈노트)이 남아 있으면 내지 않고 그걸 말한다.
AUTO_SUBMIT=on
# 심사를 통과하면 곧바로 출시 (기본 on). off 면 '출시 대기' 에서 [출시] 를 기다린다.
AUTO_RELEASE=on

# 수출 규정 준수(암호화) — 심사에 내려면 빌드마다 답이 있어야 한다.
# yes — HTTPS·iCloud 처럼 운영체제 암호화만 쓴다(면제). DeployBar 가 빌드마다 이 답을 넣는다.
# no  — 자체 암호화를 쓴다. 답은 App Store Connect 에서 사람이 한다.
# 적지 않았고 Info.plist 에 ITSAppUsesNonExemptEncryption 도 없으면, 빌드 전에 경고하고
# 업로드 뒤 심사 제출에서 멈춘다 (결과: 미완).
# ENCRYPTION_EXEMPT=yes

# 미리보기 영상의 대표 프레임(초). 영상은 docs/screenshots/preview/<로케일>/ 에 둔다.
# 적지 않으면 애플 기본값(5초).
# PREVIEW_POSTER=6
```

배포가 끝나면 로그 맨 끝에 `🏁 결과:` 한 줄이 남는다. 로그 파일도 같은 말로 닫힌다 (`━━ 끝 …`).

| 결과 | 뜻 |
|---|---|
| `✅ 성공` | 하려던 것을 끝까지 했다 (App Store 배포면 심사 제출까지, `AUTO_SUBMIT=off` 면 빌드 연결까지) |
| `⚠️ 미완` | 업로드는 됐지만 심사에 내지 못했다 — 이유와 할 일이 바로 위에 있다 |
| `❌ 실패` | 업로드 전에 멈췄다 |

기존 앱의 `fastlane/.env` 도 그대로 읽는다(하위호환). 둘 다 있으면 `deploy.env` 가 이긴다.

### 한 레포 안의 두 번째 앱 — 하위 폴더 앱

맥 앱 레포 안에 따로 올리는 아이폰 앱(예: `StickyPresenter/StickyPresenterRemote`)이 있으면, 그 하위 폴더에
**자기 `.xcodeproj` 와 `deploy.env` 를 같이** 두면 별개 앱으로 잡힌다(`deploy.env` 가 "이건 별개 앱" 이라는 선언이다 —
프로젝트만 있는 도구·예제 폴더는 잡지 않는다). 카드 이름은 폴더 이름이고, 문구·노트·그림·버전 파일은 전부 그 폴더 기준이다.

두 앱이 git 을 같이 쓰므로 DeployBar 는 각자의 몫만 본다.

- 커밋 안 된 변경·'올릴 변경 있음'·릴리즈노트 초안의 커밋: 하위 앱은 자기 폴더만, 바깥 앱은 하위 앱 폴더를 뺀 나머지만
- 직전 배포 태그: `deploy-<SCHEME>-…` 의 SCHEME 으로 가른다
- 폴더 밖인데 하위 앱의 소스인 경로(공유 프로토콜 등)는 하위 앱 `deploy.env` 의 `GIT_PATHS=../Shared` 로 더한다

### 자동 설정 — 규칙을 손으로 안 맞춰도 된다

체크리스트의 `[자동 설정]`, 카드의 `⋯ › 배포 설정 자동 정리`, 하단의 `전체 자동 설정` 이 모두 같은 일을 한다.

- `deploy.env` 가 없으면 그 앱에 맞게 만든다 (`fastlane/.env` 값이 있으면 옮겨 온다)
- 이미 있으면 **주석과 순서를 그대로 두고** 빠진 키만 채운다
- `VERSION_XCCONFIG` 경로가 틀렸으면 실제 위치를 찾아 고친다
- `scripts/predeploy.sh` 가 없으면 그 앱의 scheme·플랫폼에 맞춰 만든다
- 번역이 이미 완벽한 앱만 `LOCALIZATION_GATE=strict` 로 시작한다
  (구멍이 있는 앱을 갑자기 strict 로 바꾸면 다음 배포가 통째로 막혀 놀라게 된다)

사람이 쓴 값은 덮어쓰지 않고, 여러 번 눌러도 결과가 같다.
`⋯ › 설정 자세히 점검` 또는 CLI `--doctor` 로 규칙 하나하나를 볼 수 있다.

> 다국어 검사는 DeployBar 안에 내장돼 있으므로, 앱마다 `check_localization.py` 를 둘 필요가 없다.
> `predeploy.sh` 에는 그 앱만의 검사(테스트·금지 패턴)만 남기면 된다.

## 다국어 배포가 도는 방식

### 1. 배포 전 — 다국어 게이트

앱 폴더의 모든 `.xcstrings` 를 읽어 세 가지를 잡는다.

| 잡는 것 | 왜 |
|---|---|
| **미번역** — `LOCALES` 의 언어인데 값이 없음 | 소스 언어 문자열이 그대로 노출됨 |
| **미완료** — state 가 `new`/`stale`/`needs_review` | 원문이 바뀐 뒤 번역이 안 따라옴 |
| **한글 혼입** — 한국어 아닌 언어 값에 한글 | 영어 사용자가 한글을 봄 |

복수형·기기별 `variations` 안까지 본다. 소스 언어와 `shouldTranslate: false` 는 건너뛴다.
`LOCALIZATION_GATE=strict` 면 하나라도 있을 때 아카이브를 만들지 않는다.

### 2. 릴리즈노트 — 배포 **전**에 막고, 배포 후에 채운다

```
git pull → 다국어 게이트 → 릴리즈노트 게이트 → predeploy.sh → 버전/빌드번호
                                ↑                                    ↓
                   비어 있으면 여기서 중단              archive → export → altool
                   (빌드를 만들기도 전에)                             ↓
                                          지원 언어 조회 → 언어별 생성 → 전 언어 업로드
```

**게이트를 빌드 앞에 둔 이유**: 예전엔 릴리즈노트를 업로드 *뒤에* 채웠다. 그 단계가 실패하거나
중간에 끊기면 **'이 버전의 새로운 기능' 이 빈 채로 App Store 에 올라간 뒤였고, 되돌릴 수 없다.**
이제 편집 가능한 버전(`제출 준비`·`거부됨`)의 노트가 비어 있으면 아카이브조차 만들지 않는다.

첫 업로드 전이라 편집 가능한 버전이 아직 없으면 막지 않는다 — 막을 수가 없기 때문이다
(그 경우 업로드 뒤 자동 반영에 맡기고, 체크리스트에 ⚠️ 로 남긴다).

문구를 만드는 순서:

1. **AI** — `config.env` 에 `ANTHROPIC_API_KEY` 가 있으면, 커밋 로그로 **한 번의 호출에** 모든 언어를
   현지화해 만든다(번역이 아니라 언어권별로 자연스럽게).
2. **온디바이스 번역** — 키가 없거나 일부 언어가 비면 Apple Translation(macOS 15+)으로 한국어 원문에서 채운다.
   같은 언어의 지역 변형(`en-US`/`en-GB`)은 한 번만 번역해 재사용한다.
3. **직접 입력** — 온디바이스 번역이 지원하지 않는 언어는 비워 두고 로그에 남긴다.
   `릴리즈노트` 창에서 언어별 칸에 직접 넣으면 된다. **빈 칸은 업로드하지 않으므로 기존 문구가 유지된다.**

`릴리즈노트` 창은 App Store 가 요구하는 언어 수만큼 편집칸을 만든다.
`빈 언어 채우기` 버튼으로 한국어 원문에서 나머지를 한 번에 번역한다.

### 3. 업로드 뒤 — 빌드마다 dSYM 을 남긴다

archive 는 앱 폴더의 `build/deploy-console/<scheme>.xcarchive` 한 자리에 만들어져 **배포할 때마다 덮어써진다.**
그래서 지난 빌드에서 온 크래시 보고(MetricKit 등)는 dSYM 이 없어 함수 이름으로 풀 수 없었다.
이제 업로드가 확인되면 그 archive 의 `dSYMs/` 를 버전·빌드별로 복사해 두고, **지우지 않는다.**

```
~/Library/Application Support/DeployBar/dSYMs/<번들 ID>/<버전>(<빌드>)/
    <앱>.app.dSYM …    archive 의 dSYMs/ 그대로
    uuids.txt          dwarfdump --uuid 결과 (UUID · 아키텍처 · 경로)
```

- 버전·빌드는 archive 의 `Info.plist`(`ApplicationProperties`)에서 읽는다 — 실제로 올라간 번호다.
- 복사에 실패해도 배포는 실패하지 않는다. 로그에 ⚠️ 로만 남는다.
- 크래시 보고의 UUID 로 빌드 찾기: `$D --dsym 골드위크 <UUID>` (앱을 빼면 전체에서), 또는 `grep -ri <UUID> ~/Library/Application\ Support/DeployBar/dSYMs`.

## 스토어 페이지 — 문구와 그림도 DeployBar 가 올린다

빌드를 올리는 것과 **스토어에 나가는 것**은 다른 일이다. 여태 그 사이의 일 —
버전 만들기, 빌드 고르기, 설명·키워드 쓰기, 스크린샷 올리기, 심사 제출 — 은 전부
"App Store Connect 웹에서 사람이" 였다. 그런데 그 중 대부분은 API 가 한다.

```
[배포] 한 번으로 끝까지 — 칸마다 진행 패널에 보인다
  버전·빌드번호 ─▶ 빌드·업로드 ─▶ 스크린샷 ─▶ 릴리즈노트 ─▶ 빌드 연결 ─▶ 심사 제출 ─▶ (통과하면 출시)
  스토어 버전에 맞춤              docs/screenshots/                애플 처리 대기   막히는 게 없을 때만
  (없으면 만든다)                                                 (5~20분)
```

**배포 버튼 한 번이 심사 제출까지 간다.** 예전엔 업로드에서 멈췄고, 그 뒤에 사람이
"몇 분 기다렸다가 [빌드 연결], 그리고 [심사 제출]" 을 눌러야 했다. 판단이 필요 없는 클릭이라 도구가 한다.

- **버전 번호는 스토어를 보고 정한다.** 스토어에 준비 중인 버전(예: ASO 문구를 고치려고 만든 v2.2.9)이 있으면
  로컬이 2.2.8 이든 2.2.5 든 그 번호로 올린다. 이미 나간 번호면 그 위로 patch 를 올리고, 스토어에 준비된
  버전이 없으면 만든다. `버전 올리기` 로 번호를 고르면 스토어 쪽 준비 버전의 번호를 거기 맞춘다
  (써 둔 부제·키워드·릴리즈노트는 따라온다). 규칙 검증: `--selftest-version`, 다음 번호 미리 보기: `--todo <앱>`.
- **빌드 연결** 은 방금 올린 그 빌드 번호가 애플 처리를 마칠 때까지(최대 1시간) 기다렸다가 붙인다.
  칸에 "처리 중 · 6분째" 가 보인다. 지난 빌드가 붙어 있어도 이번 빌드로 바꾼다.
- **심사 제출** 은 사람 몫(인앱결제·연령 등급·가격·판매 지역·빈 릴리즈노트)이 하나도 없을 때만 낸다.
  남아 있으면 내지 않고 칸에 이유를, 배너에 할 일을 남긴다. `AUTO_SUBMIT=off` 면 연결까지만.
- **전체 배포** 는 업로드를 먼저 전부 끝낸 뒤 앱마다 연결·제출을 이어 한다 —
  앱마다 처리를 기다리면 줄 전체가 멈추기 때문이다. 그 사이 앞 앱들의 처리가 끝나 있어 대개 바로 붙는다.
- 배포 중에 스토어 **문구는 APPSTORE.md 에 적은 것만, 스토어에 비어 있는 칸에만** 쓴다.
  웹이나 다른 도구(FeedbackHub 의 ASO 등)로 써 둔 부제·키워드는 건드리지 않는다.

손으로 스토어 페이지만 따로 올릴 때:

```
[스토어 올리기] 페이지 채우기
  버전 생성 → 빌드 연결 → 문구 → 그림
       ↑                    ↑
 APPSTORE.md         docs/screenshots/
```

카드의 `⋯ › 스토어 페이지` 또는 체크리스트의 `[스토어 올리기]`, CLI 로는 `--publish`.
**무엇이 올라갈지 먼저 보려면 `--publish <앱> --dry-run`** — 아무것도 쓰지 않고 목록만 보여 준다.

### `APPSTORE.md` — 스토어 문구의 원본

RELEASE_NOTES.md 와 같은 생각이다. 스토어에서 사람이 읽는 글은 App Store Connect 의
입력칸이 아니라 **레포에** 있어야 한다. 그래야 커밋 이력이 남고, 번역이 리뷰를 거치고,
실수로 지워도 되돌릴 수 있다.

```markdown
## 한국어 (ko)          ← 절 제목이 언어. `## ko`·`## App Store (English)` 다 알아본다

### 이름
뇌모리

### 부제
24시간 뒤 사라지는 임시 기억

### 설명
...본문...

### 키워드
주차위치,사물함,비밀번호       ← 쉼표만. 공백을 넣으면 100자를 낭비한다

### 지원 URL
https://...

### 개인정보처리방침 URL
https://...

## 연령 등급
해당 없음               ← 이렇게 적어 둔 앱만 설문을 '전부 해당 없음' 으로 신고한다
```

- **안 적은 칸은 안 건드린다.** 빈 줄로 두면 스토어의 기존 문구가 그대로 남는다.
- **스토어에 이미 글이 있으면 기본적으로 그대로 둔다.** 웹에서 급히 고친 문구를
  도구가 말없이 되돌리는 게 더 큰 사고다. 덮어쓰려면 `--overwrite`.
- 글자 수(이름·부제 30, 설명 4000, 키워드 100, 프로모션 170)는 **올리기 전에** 잡는다.
  애플의 409 는 어느 언어의 어느 칸인지 말해 주지 않는다.
- `--storemeta <앱>` 으로 무엇을 어떻게 읽었는지 확인하고, 파일이 없으면 `--write` 로 뼈대를 만든다.

### 스크린샷 — 배포가 "지금 다시 찍을 때" 를 먼저 말한다

배포 마지막 칸이 **스크린샷 점검**이다. 두 경우에 붙여넣을 지시문을 그 자리에서 만든다.

| 언제 | 판단 근거 |
|---|---|
| 그림이 화면 변화보다 오래됐을 때 | 마지막 캡처 이후 커밋에서 화면 파일이 바뀜 |
| App Store 에 그림이 한 장도 없을 때 | 스토어 쪽을 직접 세어 본다 (첫 출시에서 제출을 막는 진짜 이유) |

```
━━ Externalize · 8/14
  ⏭ 릴리즈노트 검사   첫 출시 — 스토어에 그 칸이 없습니다
  ✅ 스크린샷 점검     App Store 에 그림이 한 장도 없습니다 — 이대로는 심사 제출이 안 됩니다
```

지시문 **전문이 로그에 남고**, 앱 하나만 배포했으면 클립보드에도 들어간다
(전체 배포에서는 앱마다 덮어쓰면 뜻이 없으므로 배너로만 알리고 로그에 남긴다).
`--check <앱>` 도 같은 판단을 돌린다 — 읽기만 하므로 배포 전에 미리 볼 수 있다.

**찍는 것은 여전히 Claude Code 다.** 시뮬레이터를 몰고 다니며 화면을 넘기는 일은
DeployBar 가 못 하고, 대신 *언제 찍어야 하는지와 무엇을 찍어야 하는지* 는 배포하는 이 자리가
제일 잘 안다. 그 둘을 글로 넘긴다. 찍어서 `docs/screenshots/` 에 두면 그때부터는 올리는 것까지 한다.

### 그림 올리기 — 배포가 알아서 한다

**배포할 때 `docs/screenshots/` 의 그림으로 스토어를 맞춘다.** 찍어서 폴더에 두고 커밋해 두면,
다음 배포가 그걸 올린다. 따로 누를 필요가 없다(급하면 `⋯ › 스토어 페이지 › [스토어에 올리기]`).

어디를 읽는지는 **관리 중인 앱들이 실제로 쓰는 모양을 그대로** 받아들인다.

| 폴더 | 뜻 |
|---|---|
| `marketing/` · `appstore-65/` · `submit/` · `final/` | **제출본** — 이게 있으면 이게 올라간다 |
| `marketing/ko/` · `marketing-ko/` | 제출본 · 그 언어에만 |
| `ko/` · `en/` | 언어별 |
| `docs/screenshots/*.png` | 한 벌 — 모든 언어에 같은 그림 |
| `raw/` · `seed/` | 원본 — **올라가지 않는다** |

**제출본이 원본을 이긴다.** 거의 모든 앱이 시뮬레이터 원본(1320×2868)과 헤드라인을 붙인
제출본(1242×2688)을 같은 폴더 아래 두는데, 크기만 보면 둘 다 규격이라 원본이 올라가는 사고가 난다.
그래서 폴더 이름으로 먼저 가른다.

기기 판별은 **픽셀로만** 한다 — 파일 이름은 믿지 않는다(시뮬레이터가 뱉는 이름은 제각각이고,
규격에 안 맞는 그림은 애플이 통째로 거부한다). 파일 이름 순서가 곧 스토어에서 보이는 순서다.
이미 올라간 것과 이름·크기가 같으면 다시 올리지 않는다(한 장에 수 MB 라 느리다).

```bash
$D --shotplan 두번알림    # 무엇이 어느 기기 자리에 올라갈지 (네트워크 없이)
```
```
/Users/…/두번알림/docs/screenshots
── 모든 언어 · iPhone 6.9" (APP_IPHONE_67) · 5장
   1. 01-main-timer.png   2. 02-timer-running.png   …
```

찍는 건 여전히 Claude Code 다 (`⋯ › 앱스토어 그림 프롬프트` · `--shots`).
**만들지는 않고, 올리기는 한다.**

**워치 그림도 올린다.** `docs/screenshots/watch/` (안쪽 모양은 아이폰과 같다 — `watch/ko/`, `watch/marketing/`)를
따로 읽어 같은 언어 칸의 Apple Watch 자리에 넣는다. 기기는 픽셀로 가른다 (416×496 → Apple Watch 46mm 등).

**배포는 기본으로 기존 그림을 건드리지 않는다.** 비어 있는 칸만 채운다 — 스크린샷은 매번 바꾸는 게 아니다.
바꿀 때는 카드의 스크린샷 뱃지를 누르거나 배포 메뉴에서 **`이번 배포에서 스크린샷 교체`** 를 체크한다
(버튼이 `배포 + 그림` 으로 바뀐다). 그러면 배포가:

1. 스토어 페이지의 **모든 언어**에 아이폰 그림이 있고 규격이 맞는지 먼저 본다.
2. 다 되어 있으면 기존 스크린샷을 **기기 가리지 않고 전부** 지우고 레포 그림으로 올린다.
3. 하나라도 빠졌으면 **아무것도 지우지 않고**, 심사 제출도 멈춘다 (옛 그림으로 심사가 시작되면 안 되므로).
   체크는 남아 있어서 그림을 채우고 다시 누르면 된다. 성공하면 체크가 꺼진다.

카드의 뱃지가 준비 상태를 말한다: 초록 `✓ 📱4 ⌚4` = 준비됨, 주황 = 빠진 언어·규격 밖 파일·낡음,
파랑 `교체` = 이번 배포에서 교체, 빨강 `교체` = 교체를 체크했지만 준비가 덜 됨.

### 미리보기 영상 올리기, 그림과 같은 규칙

**검색 결과 첫 칸에 소리 없이 자동 재생되는 영상**도 레포에서 올린다. 자리는 하나로 정해 둔다.

```
docs/screenshots/preview/<로케일>/app-preview.mp4    언어별 (권장. 자막이 그 언어여야 그 나라 검색에서 읽힌다)
docs/screenshots/preview/app-preview.mp4             모든 언어에 한 벌
```

- 로케일 폴더는 스토어 로케일(`en-US` · `es-MX` · `ko`)이다. 정확한 폴더가 없으면 **같은 언어** 폴더를 쓴다(`en-US` → `en-GB`).
- 한 칸에 세 개까지, 파일 이름 순서가 스토어 순서다.
- 기기 칸은 **픽셀로** 가른다: 886×1920 → 아이폰(그 언어의 아이폰 스크린샷과 같은 6.5"/6.9" 칸), 1200×1600 → 아이패드 13".
- 대표 프레임(자동 재생이 꺼진 기기에 보이는 한 장)은 `deploy.env` 의 `PREVIEW_POSTER=<초>`. 애플이 영상 처리를 끝낸 뒤에만 받으므로,
  다 올린 다음 처리를 최대 10분 기다렸다가 맞춘다. 그 안에 안 끝나면 다음 `--publish` 가 맞춘다.
- **올리기 전에 애플이 거절할 영상을 먼저 걸러 낸다**: 길이 15~30초, 500MB 이하, **소리 트랙**(무음이어도 있어야 한다).
  소리 트랙이 없거나 색 태그가 sRGB 면 애플은 처리 뒤에 "손상된 파일" 로 돌려보내는데, 그때는 어느 파일인지 알기 어렵다.
- 그림과 같이, 배포는 **비어 있는 칸만 채운다.** 바꾼 영상을 올리려면 `이번 배포에서 스크린샷 교체` 를 체크하거나 `--publish`.
  이름·크기가 같은 영상은 다시 올리지 않는다.

```bash
$D --shotplan 클립키보드    # 끝에 '미리보기 영상' 줄: 언어 · 칸 · 파일 · 걸러 낸 이유
```
```
미리보기 영상 14개 · 대표 프레임 00:00:06:00
   ✅ ko · iPhone 6.5" · app-preview.mp4
   ✅ en-US · iPhone 6.5" · app-preview.mp4
```

### 헤더 · 검색 결과 올리기 (크리에이티브 자산)

iOS·iPadOS 27 부터 제품 페이지 맨 위에 **헤더** 한 장, 검색 결과에 스크린샷 대신 **검색 결과** 한 장이 뜬다.
애플은 비워도 받지만(검색 결과는 스크린샷이 대신 나간다) **우리 기준에서는 스크린샷과 같은 필수 항목이다.**
`--prepare` 는 iOS 앱에 이 그림이 언어마다 없으면 '헤더·검색 결과' 갈래로 미완을 낸다(카드 체크리스트·국기에도 뜬다).
레포에 두면 배포가 함께 올리고, 버전과 같이 심사받는다.

```
docs/screenshots/creative/<로케일>/header.png    언어별 헤더
docs/screenshots/creative/<로케일>/search.png    언어별 검색 결과
docs/screenshots/creative/header.png             모든 언어에 같은 그림
```

- **칸마다 따로 빌려 온다**: 정확한 로케일 → 같은 언어(`en-US` → `en-GB`) → 모든 언어. 헤더는 한 벌, 검색 결과만 언어별 같은 섞어 쓰기가 된다.
- 어느 칸인지는 **이름이 먼저**(`header…` · `search…`), 이름이 말하지 않으면 픽셀로 가른다.
  같은 폴더에 같은 칸 파일이 둘이면 이름순 첫 파일만 쓰고 나머지는 경고한다.

| 칸 | 크기 | 형식 |
|---|---|---|
| 헤더 | 3840×1646 (21:9) | PNG · 또는 같은 크기 영상 |
| 검색 결과 | 3:2, 1920×1280 ~ 3840×2560 | PNG · JPEG · 또는 같은 비율 영상 |
| 둘 다 | 5244×2950 (16:9) | PNG (한 파일이 두 칸에 들어간다) |

- 영상은 5~30초, 30·60fps, 500MB 까지. 소리 없이 반복 재생된다. 대표 프레임은 `PREVIEW_POSTER` 가 영상 길이 안이면 그 값.
- **투명(알파) 채널이 있으면 애플이 거절한다.** 올리기 전에 크기·비율·형식·알파·길이·프레임을 먼저 걸러 경고로 남긴다.
- 규격은 하드코딩하지 않고 애플의 규격 목록(`/v1/appAssetLibraryRefData`)에서 읽는다. 못 읽을 때만 내장 사본(2026-10)을 쓴다.
- 이 칸은 **자산 라이브러리**를 거친다: 파일을 라이브러리에 한 번 올리고 언어마다 배치한다. 모든 언어 한 벌이면 업로드도 하나다.
  라이브러리 이름표 `DeployBar <파일> <해시>` 로 같은 파일을 알아보므로, 다음 배포에도 다시 올리지 않는다.
- 그림과 같이, 배포는 **비어 있는 칸만 채운다.** 바꾼 그림을 올리려면 `이번 배포에서 스크린샷 교체` 를 체크하거나 `--publish`.
  바꿀 때 DeployBar 가 올렸고 아직 심사 전인 옛 자산은 라이브러리에서 지운다(사람이 웹에서 올린 것은 그대로 둔다).
- 다 올린 뒤 애플의 처리를 최대 10분 기다린다. 처리에 실패한 자산은 칸을 비우고 이유를 경고한다(실패한 자산이 남으면 심사 제출이 막힌다).
- 이 단계가 실패해도 배포는 멈추지 않는다. 비워도 되는 칸이라 경고로만 남긴다.

```bash
$D --shotplan 클립키보드    # 끝에 '헤더·검색 결과' 줄: 언어 · 칸 · 파일 · 걸러 낸 이유 · 빠진 언어
```

**만들기**: 카드 `⋯ ▸ 앱스토어 그림 프롬프트 복사 ▸ 헤더·검색 결과 만들기` (또는 `$D --shots <앱> --creative`)가 지시문을 복사한다.
본보기는 클립키보드의 `scripts/make_creative_assets.py` 다(HTML → 헤드리스 Chrome). 생성 스크립트가 없는 앱에는
그 파일을 복사해 고쳐 쓰라고 적어 준다. 지시문에 담기는 규칙:

- 글은 **안전 영역** 안에만 둔다(Apple PSD 템플릿에서 잰 값). 헤더 (1097,493)–(2743,1154), 검색 결과 3840×2560 (836,765)–(3004,1795).
- 헤더는 **한 가지 약속**, 검색 결과는 **스크린샷 1장과 같은 이야기**. 눈썹글은 그 나라 검색어다.
- 바탕·글자색은 스크린샷과 같게. 문구는 언어마다 따로 쓰고, 안전 영역을 넘으면 그림을 만들지 않고 멈춘다.
- 가격·할인·URL·수상·다른 플랫폼 이름은 넣지 않는다.

### 레포가 원본이다 — 스토어에 있던 글보다 레포 글이 이긴다

`APPSTORE.md` 에 적힌 칸은 App Store Connect 의 값과 다르면 **레포 글로 바꾼다**. `RELEASE_NOTES.md` 에 쓴 언어도 같다.
예전엔 칸이 이미 차 있으면 건드리지 않았는데, 그 탓에 언어를 추가할 때 임시로 들어간 값(한국어 이름 등)이
남아 독일어 페이지가 한국어로 나갔다 — 로그에 아무 말 없이. 이제 바꾸기 전 값은 로그와
`~/Library/Application Support/DeployBar/store-backup/<앱>-<시각>.json` 에 남는다.

### 배포 준비 — 자동 배포 완비 기준

`⋯ › 배포 준비 지시문 복사` (`--prepare <앱>`) 는 "버튼 한 번으로 심사까지 가려면 레포에 무엇이 다 있어야 하나" 의
기준과, 그 앱에서 지금 빠진 것을 Claude Code 에 붙여넣을 지시문으로 낸다. 끝 줄이 판정이다
(`✅ 자동 배포 완비` / `❌ 미완 — 빠진 것 N개`).

- 언어마다: 스토어 문구 7칸(이름·부제·키워드·프로모션·설명·지원 URL·개인정보 URL), 배포할 버전의 릴리즈노트, 그 언어 스크린샷
- 워치 앱이 있으면 워치 그림, 본체가 아이패드를 지원하면 아이패드 그림까지
- 한도·한글 섞임·이름 단어를 반복하는 키워드·열리지 않는 URL·LOCALES 에 빠진 번역 언어·커밋 안 된 변경
- 사람만 할 수 있는 신고(첫 출시의 연령 등급 등)는 따로 적는다

같은 기준이 카드에도 뜬다 — 갈래(설정·스토어 문구·릴리즈노트·스크린샷)마다 ⚠️ 권장 한 줄씩. 배포를 막지는 않는다.

**새 언어를 늘릴 때**는 `--prepare <앱> --lang <로케일>` 이 그 언어 하나만 다루는 지시문을 낸다
(LOCALES 추가 → 앱 번역 → `APPSTORE.md` 절 → 릴리즈노트 절 → 그 언어 스크린샷, 끝 줄 `✅ <언어> 완비`).
카드에선 빈 곳이 남은 언어의 국기가 흐려지고, 누르면 같은 지시문이 복사된다. 앱만 번역하고 LOCALES 에 안 넣은
언어도 흐린 국기로 끝에 붙는다. 스토어에 그 언어 페이지가 없으면 배포가 시작될 때 만든다 — 웹에서 추가할 필요 없다.

사용자 CLAUDE.md 의 '배포 준비' 규칙이 이 명령을 부른다 — 기준을 고칠 곳은 `DeployPrep.swift` 하나다.

### 스토어 문구 자동 작성 — 언어마다 쓰기 어려운 글을 AI 가

`⋯ › 스토어 페이지 › 스토어 문구 자동 작성` (`--autowrite <앱>`) 은 **비어 있는** 이름·부제·키워드·
프로모션 텍스트·설명과 이번 버전 릴리즈노트를 `deploy.env` 의 `LOCALES` 전부로 써서
`APPSTORE.md` · `RELEASE_NOTES.md` 에 채우고 그 두 파일만 커밋한다. 올리는 건 늘 하던 대로 배포가 한다.

- **빈 칸만.** 레포에 적힌 글도, App Store Connect 에 이미 있는 글도 건드리지 않는다.
- **한국어가 출발점.** 한국어가 비면 README·커밋을 보고 먼저 쓰고, 다른 언어는 그걸 그 언어권에 맞게 다시 쓴다
  (키워드는 직역하지 않고 그 나라 사람이 치는 말로).
- **릴리즈노트는 배포가 쓸 번호의 절에.** 로컬이 2.2.9 여도 스토어에 2.3.0 이 준비돼 있으면 `## 2.3.0` 에 쓴다.
- **한도는 도구가 지킨다.** 이름·부제 30, 키워드 100, 프로모션 170, 설명 4000 — 넘으면 한 번 다시 쓰게 하고, 그래도 넘으면 비워 두고 말한다.
- AI 는 `config.env` 에 `ANTHROPIC_API_KEY` 가 있으면 API 를, 없으면 이 Mac 의 `claude` CLI(Claude Code)를 쓴다 — 키 없이도 돈다.

```bash
$D --autowrite 두번알림 --dry-run    # 무엇을 쓸지 미리보기 (파일 안 씀)
$D --autowrite 두번알림              # 쓰고 커밋 (--no-commit 이면 커밋 안 함)
```

### 심사 제출 · 출시

- `⋯ › 스토어 페이지 › 심사 제출` — 한 겹 더 눌러야 닿는다. 여기서부터 애플이 보고,
  되돌리려면 심사를 취소해야 하기 때문이다. 빌드가 연결돼 있지 않으면 미리 막는다.
- 심사를 통과해 `출시 대기` 가 되면 `지금 출시` 가 나타난다 (웹의 [출시] 버튼과 같다).
- CLI: `--submit <앱>` · `--release <앱>`

### 첫 배포를 누르면 — 사람 몫을 그 자리에서 안내한다

업로드가 끝났다고 스토어에 나가는 게 아니다. 첫 출시는 연령 등급·인앱결제·가격·판매 지역·
개인정보 라벨이 비어 있으면 **제출 버튼이 아예 안 눌리는데**, 그걸 웹에 가 보고서야 알면
"올렸는데 왜 아무 일도 안 일어나지" 가 된다. 그래서 배포가 끝나는 자리에서 말한다.

```
🙋 첫 출시입니다 — 여기서부터는 사람이 App Store Connect 웹에서 해야 합니다 (5가지)
   1) 연령 등급 설문 — 애플에 하는 내용 신고라 사람이 판단합니다
   2) 인앱결제 만들기 — com.devkoan.externalize.lifetime · 값이 돈이라 도구가 정하지 않습니다
   3) 가격 정하기 · 4) 판매 지역 · 5) 앱 개인정보 라벨
   · 나머지 3가지는 ⋯ ▸ 스토어 페이지 ▸ [스토어에 올리기] 가 합니다
```

같은 내용이 **✕ 로 지울 때까지 남는 배너**로도 뜨고, 체크리스트에도
⚠️ `사람이 웹에서 해야 하는 일 5가지` 로 남는다(배포는 막지 않는다 — 업로드는 되니까).
`--todo <앱>` 으로 언제든 다시 본다. **업데이트 앱에는 아예 뜨지 않는다** —
가격·지역·라벨은 지난 버전 값이 그대로 따라오므로 물어볼 이유가 없다.

### 첫 출시 앱은 체크리스트가 따로 말한다

아직 한 번도 판매된 적 없는 앱만, 스토어 페이지가 찼는지 같이 본다 —
`⚠️ 스토어 페이지 미완성 — 설명 없음 · 스크린샷 없음 · 연령 등급 미작성`.
빌드도 올라갔고 릴리즈노트도 됐는데 웹에 가 보면 제출 버튼이 회색인 이유가 대개 여기 있다.
업데이트 앱에는 묻지 않는다(지난 버전 값이 따라오므로). 그래서 조회가 늘지 않는다.

> **첫 버전에는 '이 버전의 새로운 기능' 칸이 없다.** App Store 가 업데이트에만 그 칸을 만들기 때문이다.
> 그래서 첫 출시에는 릴리즈노트 게이트를 건너뛴다 — 없는 칸을 비었다고 막으면
> 사람이 무슨 글을 써도 풀 수 없는 잠김이 된다.

## 설정 (`~/Library/Application Support/DeployBar/`)

- `apps.json` — 관리 앱 목록 (폴더 자동 발견 결과 + 수동 등록분)
- `changes.json` — 변화 히스토리 (✕ 로 지우기 전까지, 최근 30건)
- `status-cache.json` — 지난 조회 결과. 다음 실행 때 이것과 견줘 변화를 찾는다
- `hidden.json` — 관리에서 잠시 뺀 앱
- `logs/` — 배포·점검 실행 로그. **창을 닫아도 남는다** (최근 80건, 오래된 것부터 삭제).
  로그 창의 `📄` 버튼이 이 파일을 Finder 에서 열고, CLI 는 `--logs` / `--logs last`.
  업로드가 거부되면 애플이 남긴 원문 로그(`~/Library/Logs/ContentDelivery/com.apple.itunes.altool`)
  에서 사유를 한 줄 더 읽어 실패 패널에 붙인다
- `dSYMs/<번들 ID>/<버전>(<빌드>)/` — 업로드한 빌드마다 남긴 dSYM 과 `uuids.txt`. **지우지 않는다** (`--dsym`)
- `config.env` (선택) — `ANTHROPIC_API_KEY`(AI 릴리즈노트), `ANTHROPIC_MODEL`, ASC 키 재정의 등

ASC 키는 `~/Documents/workspace/fastlane-shared/asc.env` 재사용,
`.p8` 은 `~/.appstoreconnect/private_keys/AuthKey_<KEYID>.p8` 에서 탐색.

## 폰에서 배포하기 — `--deploy` · `--ready`

이 Mac 에서 도는 Claude Code 세션을 폰으로 이어 쓰면(Remote Control) "달빛 배포해줘" 한마디로 배포가 된다.
세션이 부르는 명령은 둘이다.

```bash
D=/Applications/DeployBar.app/Contents/MacOS/DeployBar
$D --ready                       # 배포 가능 · 심사 중 · 막힌 앱 (떠 있는 앱이 들고 있는 상태로 바로 답한다)
$D --deploy 달빛                  # 배포 버튼과 똑같이 — 끝날 때까지 로그를 흘리고 결과 한 줄
$D --deploy 달빛 --bump patch     # 버전 올려서
$D --deploy 달빛 --check          # 게이트까지만 (업로드 없음)
```

- 배포를 돌리는 건 **떠 있는 DeployBar 창 앱**이다. 명령은 요청만 넘긴다(DistributedNotification). 그래서 진행판·알림·로그가
  창에도 그대로 뜨고, 앱이 꺼져 있으면 명령이 띄운다(`open -g` — 화면을 뺏지 않는다).
- 버튼과 같은 규칙으로 거절한다: 막힌 앱, 심사 중인 앱(올리면 심사가 취소된다), 이름이 모호할 때, 다른 배포가 도는 중일 때.
  `--bump` 를 주면 '올릴 변경 없음' 하나는 넘는다 — 버전을 올리는 것 자체가 올릴 것이다.
- 끝 코드: `0` 성공 · `2` 미완(업로드는 됐지만 심사에 못 냄) · `1` 실패 · `3` 거절. 처리 대기까지 길면 한 시간 — 기본 90분 기다린다
  (`--timeout <분>`, `--no-wait` 면 시작만 확인하고 끝, `--quiet` 면 로그를 흘리지 않는다).

## CLI 모드

UI 없이 확인만 할 때 쓴다.

```bash
D=DeployBar.app/Contents/MacOS/DeployBar
$D --status              # 앱별 배포 준비 N/M + 체크리스트 전체 (❌ 막는 것 / ⚠️ 권장 / ✅ 통과)
$D --doctor              # 전체 앱의 배포 규칙 점검
$D --doctor 두번알림      # 앱 하나만
$D --template 두번알림    # 설치될 deploy.env·predeploy.sh 미리보기 (파일 안 씀)
$D --template 두번알림 --write   # 실제로 설정 (UI 의 [자동 설정] 과 동일)
$D --prompt 두번알림      # 잠김 해결 지시문 (UI 의 [해결 프롬프트] 와 같은 글)
$D --prompt 두번알림 | pbcopy   # 바로 클립보드로
$D --notes 두번알림       # 언어별 릴리즈노트 초안 미리보기 (업로드 안 함)
$D --shots 두번알림       # 앱스토어 스크린샷 다시 찍을 때 붙여넣을 지시문
$D --shots 두번알림 --video      # 미리보기 영상 쪽 지시문
$D --shots 두번알림 | pbcopy     # 바로 클립보드로
$D --storemeta 두번알림    # APPSTORE.md 를 어떻게 읽는지 (--write 면 뼈대 생성)
$D --shotplan 두번알림     # 그림이 어느 기기 자리에 올라갈지 (네트워크 없음)
$D --autowrite 두번알림    # 빈 스토어 문구·릴리즈노트를 모든 언어로 써서 레포에 채움 (--dry-run · --no-commit)
$D --prepare 두번알림      # 자동 배포 완비 기준 검사 + 배포 준비 지시문 (끝 줄이 판정)
$D --todo 두번알림        # 제출까지 남은 일 — 도구가 할 것 / 사람만 할 수 있는 것
$D --publish 두번알림 --dry-run   # 스토어 페이지에 무엇이 올라갈지만 (쓰지 않음)
$D --publish 두번알림      # 문구·스크린샷·버전·빌드 연결을 실제로 반영
$D --publish 두번알림 --overwrite # 스토어에 이미 있는 글까지 레포 글로 덮어쓴다
$D --publish 두번알림 --replace-shots --dry-run  # 스크린샷 교체 미리보기 (모든 언어 준비됐나 → 전부 지우고 올리기)
$D --attach 두번알림       # 올라간 빌드를 App Store 버전에 연결
$D --submit 두번알림       # 심사 제출 (여기서부터 애플이 본다)
$D --release 두번알림      # '출시 대기' 를 지금 출시
$D --logs                 # 지난 배포·점검 로그 목록 (❌ 가 붙은 게 실패한 실행)
$D --logs last            # 가장 최근 실행 로그 전체
$D --dsym 골드위크          # 보관한 dSYM — 버전·빌드 목록 (읽기만)
$D --dsym 골드위크 <UUID>   # 크래시 보고의 UUID 가 어느 버전·빌드인지, dSYM 경로까지
$D --selftest-lock        # '무엇이 배포를 잠그는가' 규칙 검증 (조회 실패는 잠그면 안 된다)
$D --selftest-changes     # 상태 변화 알림 규칙 검증
$D --help                 # 명령 목록
```

모르는 `--` 명령을 주면 창을 띄우지 않고 사용법만 출력한 뒤 종료 코드 2 로 끝난다.

## 상태가 바뀌면 알려 준다

배포를 눌렀을 때만 알림이 오면, 정작 기다리는 소식은 앱을 열어 봐야 압니다.
그건 앱이 이미 알고 있는 사실이므로 **알아낸 순간에** 배너로 말합니다.

| 알리는 것 | 문구 |
|---|---|
| 스토어 버전이 올라감 | 🎉 두번알림 v2.2.2 출시됨 |
| 심사 통과 (출시 대기) | ✅ 두번알림 심사 통과 — '출시' 를 누르면 나갑니다 |
| 거부됨 | ⚠️ 두번알림 거부됨 — 사유를 확인하세요 |
| 심사 시작 · 심사 대기 진입 | 두번알림 심사 시작 |
| 막혀 있던 앱이 풀림 | 두번알림 배포 가능 — 커밋되지 않은 변경이 해결됐습니다 |
| 업로드 완료 · 실패 | ✅ 업로드 완료 / ❌ 배포 실패 |

알림은 **콘솔 맨 위에 배너로** 뜨고 **✕ 로 지울 때까지 남습니다 — 앱을 껐다 켜도 남습니다**
(`changes.json`). 메모리에만 두면 재시작 한 번에 "그때 뭐가 풀렸더라" 를 잃습니다.
앱이 꺼져 있는 동안 생긴 변화도 다음 실행 때 지난 조회 결과와 견줘 알려 줍니다.
시스템 알림 권한이 꺼져 있어도 보입니다 — 권한 알림은 앱이 뒤에 있을 때를 위한 보조입니다.
셋까지 펼쳐 보이고 나머지는 `이전 N건 더 보기` 로 접힙니다. 왼쪽 색 막대가 성격을(초록 좋은 소식 ·
주황 손봐야 할 것 · 파랑 진행), 제목 옆 시각이 언제 온 소식인지 말합니다.

**창을 안 열어 놔도 알 수 있게 15분마다 다시 조회합니다** (배포 중에는 건드리지 않습니다).
빌드 설정은 잘 안 바뀌므로 `xcodebuild` 를 다시 돌리지 않고 App Store Connect 만 다시 봅니다.

### 조회할 때 원격도 본다

조회는 늘 `git fetch` 로 시작합니다. 이게 없으면 앞선/뒤처진 커밋 수는 **마지막으로 fetch 한
시점** 기준이라, 다른 Mac 이나 동료가 올린 커밋이 쌓여도 화면은 "원격과 동기화됨" 이라고 말합니다.
그 사이 다른 곳에서 배포가 나갔으면 `로컬이 스토어보다 낮음` 으로 막힌 채, 무엇을 하면 풀리는지도
알 수 없습니다.

받아오기(`git pull --ff-only`)는 **[새로고침] 을 눌렀을 때만** 합니다.
15분마다 도는 자동 조회까지 파일을 바꾸면 Xcode 로 보고 있던 코드가 말없이 달라집니다.

| 저장소 상태 | 새로고침이 하는 일 |
|---|---|
| 깨끗 · 원격보다 뒤처지기만 함 | 받아옵니다 → 막혀 있던 앱이 그대로 배포 가능이 되기도 합니다 |
| 저장 안 된 변경이 있음 | 손대지 않고 `원격에 새 커밋 N개 — 못 받음` 으로 남깁니다 |
| 원격과 갈라짐 | 손대지 않습니다 (`git pull --rebase` 는 사람이 판단할 일입니다) |
| 원격을 못 봄 | `원격 확인 실패` — 숫자가 옛 값임을 밝힙니다 |

앞당기기(fast-forward)만 하므로 병합 커밋도 충돌도 만들지 않고, 안 되면 그냥 실패합니다.
자격증명을 물어보는 프롬프트는 모두 끄고 20초 뒤 끊습니다 — 저장소 하나가 새로고침 전체를
멈춰 세우지 않게. (키체인에 저장된 자격증명은 그대로 씁니다)

받아온 것이 있으면 배너에 `최신 코드 받음 — 커밋 N개` 로 남습니다.
"어제는 막혀 있던 앱이 왜 갑자기 배포 가능이지" 를 설명할 한 줄입니다.

`--status --pull` 로 터미널에서도 같은 일을 할 수 있습니다.

첫 조회에는 알리지 않습니다 — 견줄 과거가 없는데 알리면 앱을 켤 때마다 배너가 쏟아집니다.
배너를 놓쳐도 콘솔 위쪽에 마지막 변화가 한 줄 남습니다.

규칙은 `--selftest-changes` 로 검증합니다 (8가지 경우).

## 상태 뱃지

| 뱃지 | 조건 |
|---|---|
| 🟠 배포 잠김 | 체크리스트에 ❌ 가 하나라도 있음 — `[🔒 잠김 N]` 을 눌러 이유를 본다 |
| 🔴 오류 | 프로젝트·빌드 설정을 못 읽음 — `[왜 안 되나]` 를 눌러 이유를 본다 (버튼 없이 침묵하지 않는다) |
| 🔵 배포 가능 | ❌ 없음. 권장(⚠️)은 남아 있어도 배포는 된다 |
| 🟢 배포 가능 | ❌ 도 ⚠️ 도 없음 — 10가지 전부 통과 |
| 🟢 배포됨 | 로컬 ≤ 라이브. 올릴 게 없다 |

심사·제출 상태(제출 준비·심사 대기·거부됨 …)는 **버전 줄에** `· 스토어 제출 준비` 로 붙는다.
메인 배지 자리를 내주지 않는 이유: App Store 가 "제출 준비" 여도 내 쪽은 커밋조차 안 돼 있을 수 있다.

## 한계

`--todo <앱>` 이 남은 일을 **도구가 할 것 / 사람만 할 수 있는 것** 으로 갈라 보여 준다.
대부분을 도구가 하게 된 뒤로는, 남은 몇 가지가 정말 사람 몫인지 버튼을 안 누른 것인지가
헷갈리기 시작했기 때문이다 — 헷갈리면 사람은 둘 다 안 한다.

**사람이 웹에서 해야만 하는 것** (나머지는 전부 API 로 한다 — 위의 '스토어 페이지' 참고):

- **앱 레코드 생성** — App Store Connect API 에 앱을 만드는 엔드포인트가 없다. 처음 한 번만.
- **앱 개인정보(데이터 수집) 라벨** — 공개 API 에 없다. 한 번 답하면 다음 버전부터 따라온다.
- **인앱결제 상품 · 가격 · 판매 지역** — API 로 만들 수는 있지만 값이 돈이라 도구가 지어내지 않는다.
  코드가 부르는 상품이 ASC 에 없으면 `--publish` 와 `--todo` 가 상품 ID 를 짚어서 알려 준다.
